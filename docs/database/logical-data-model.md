# Logical Data Model

## Scope and ownership

The application owns the data required to manage bank accounts, current balances, and financial movements.

The logical model is intentionally simplified for the current scope and consists of two core entities:

- Account
- Movement

A transfer remains a business operation, but it is not represented as a separate persisted entity.

Instead, each successful transfer is represented by two related financial movements:

- One `DEBIT` movement for the source account.
- One `CREDIT` movement for the destination account.

Both movements are correlated through the same `operationId`.

The account balance is maintained directly within the Account entity rather than being modeled as a separate balance entity.

## Entities

### Account

- Purpose: Represents a bank account and its current available balance.
- Identity: `id`
- Lifecycle: Created through the account creation API and retained permanently within the current scope. Account update and deletion are not supported.
- Attributes:
  - `id` — Unique account identifier, integer, required.
  - `name` — Customer/account holder name, string, required.
  - `balance` — Current account balance, decimal monetary value, required, must be greater than or equal to zero.
  - `createdAt` — Date and time when the account was created, timestamp, required.

### Movement

- Purpose: Represents an individual financial debit or credit applied to an account.
- Identity: `id`
- Lifecycle: Created as part of a successful financial operation and retained as part of the account's financial history.
- Attributes:
  - `id` — Unique movement identifier, required.
  - `accountId` — Account affected by the movement, required.
  - `operationId` — Identifier used to correlate movements belonging to the same financial operation, required.
  - `type` — Financial movement type, required. Allowed values: `CREDIT` or `DEBIT`.
  - `amount` — Monetary value of the movement, decimal, required, greater than zero.
  - `createdAt` — Date and time when the movement occurred, timestamp, required.

## Relationships and invariants

- An Account may have zero or many Movements.
- A Movement belongs to exactly one Account.
- Every Account referenced by a Movement must exist.
- A Movement amount must always be greater than zero.
- Movement direction is represented exclusively by the `type` attribute:
  - `DEBIT` reduces the account balance.
  - `CREDIT` increases the account balance.
- Monetary amounts themselves must not be stored as negative values.
- A successful transfer generates exactly two Movements.
- Both Movements generated by the same transfer must have the same `operationId`.
- One Movement must be a `DEBIT` associated with the source Account.
- One Movement must be a `CREDIT` associated with the destination Account.
- The source and destination Accounts must be different.
- The debit and credit amounts must be identical.
- A transfer must never result in the source Account having a negative balance.
- Account balance must always represent the current committed financial state of the Account.
- Balance updates and the corresponding Movements must form a single atomic financial operation.
- A failed transfer must not leave any persisted Movement or partial balance update.
- Duplicate processing of the same logical transfer must not generate duplicate financial effects.

Logical relationship:

`Account 1 ─── N Movement`

Logical transfer representation:

`operationId X`

- `Movement A → Account A → DEBIT`
- `Movement B → Account B → CREDIT`

There is no separate persisted `Transfer` entity in the current model.

## Sensitive data and retention

Account balances and financial movements are considered sensitive financial data.

- Access must be restricted to authorized application operations.
- Financial values must not be unnecessarily exposed in application logs.
- Movement records must be retained to preserve financial traceability.
- Account deletion is not supported in the current scope.
- Movement deletion is not supported.
- Historical financial movements must not be modified after successful completion except through explicitly defined corrective business processes, which are outside the current scope.
- The `operationId` must be retained with both movements to allow a complete financial operation to be reconstructed and audited.

## Physical mapping notes

The physical database mapping must preserve the following intent:

- `Account.id` must map to a PostgreSQL `BIGINT` identity primary key.
- `Movement.id` must map to a PostgreSQL `BIGINT` identity primary key.
- `Movement.accountId` must reference `Account.id` through a non-cascading foreign key.
- `operationId` must use PostgreSQL `UUID` and be indexed to allow both sides of a financial operation to be retrieved efficiently.
- At most one `DEBIT` and one `CREDIT` Movement may exist for the same `operationId`; application behavior remains responsible for creating exactly one of each atomically.
- Monetary values must use `NUMERIC(19,2)` storage and must not use floating-point types.
- Audit timestamps must use `TIMESTAMPTZ` so persisted instants remain unambiguous across runtime time zones.
- Account names must use `VARCHAR(255)` and reject null, empty, or whitespace-only values.
- Account balance must be stored directly on the Account record.
- Movement type must be constrained to the supported `CREDIT` and `DEBIT` values.
- Foreign keys and indexes must support efficient account movement queries.
- Movement lookup must support efficient filtering by:
  - Account.
  - Date/time range.
  - Movement type.
- The relationship from Movement to Account should be treated as lazy-loaded at the persistence layer unless a specific use case requires eager retrieval.
- The Account entity does not need to expose or eagerly load its complete movement collection for normal account operations.
- Database migrations must preserve these relationships, constraints, indexes, and financial invariants.
- The initial physical schema contains only Account and Movement storage. Transfer idempotency-token persistence and notification/outbox persistence require their own feature scope and data-model update before a later migration introduces them.
